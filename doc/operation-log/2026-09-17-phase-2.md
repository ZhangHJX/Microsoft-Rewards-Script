# Phase 2: reject unavailable flyout balances

- updated_at: 2026-09-17
- author: Codex
- status: first-slice-complete; broader-balance-contract-pending

## Change and evidence

The production FlyoutDashboard mapper now accepts only nonnegative safe-integer balances. A valid primary value, including zero, takes precedence. An invalid primary value uses a valid fallback. If neither is valid, mapping throws a sanitized `BALANCE_UNAVAILABLE` error rather than returning a fabricated zero.

Existing BrowserFunc flyout handling logs and rethrows mapping errors. This prevents the failed mapping from returning a dashboard to dependent callers. It does not yet guarantee a failing top-level process exit status; that remains a separate open requirement.

Replaced the two defect-characterization expectations with desired behavior and expanded boundary tests. Before the fix, 19 of 27 parser tests failed and 8 passed. After the fix, all 27 pass. Existing offline tests remain 36/36 passing (63 total). Full TypeScript build, targeted ESLint, formatting and diff whitespace checks passed on the same macOS/Node environment as phase 1.

## Reassessment

The next balance slice must cover the primary dashboard path: BrowserFunc currently accepts any response containing a dashboard without checking its balance. It must also cover direct getCurrentPoints consumers. Other lifetime metrics still use upstream coercion and are outside this patch. Source/timestamp tracking, failure aggregation, persistent blocks and notification deduplication remain unfinished.

Strict numeric validation intentionally treats numeric strings as a schema mismatch, rather than guessing. No live payload evidence was available to establish a string-valued contract. Real service compatibility remains unverified.

This slice changes data validation only. No real account was used and no login, task, notification or deployment was run. Phase 1 reports remain historical evidence; its two flyout defects are now fixed in this slice, not still open in current code.
